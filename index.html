ACLs in 60 Seconds

An access control list (ACL) is an ordered list of rules a Cisco router or switch uses to pick out packets and decide what happens to them. Each rule (an ACE, access control entry) says permit or deny and describes packets by fields such as source address, destination address, protocol and port.

Not sure what an ACL in front of you does? Paste it into the ACL Decoder: it explains each line in plain English and can test a packet against it.

An ACL is the guest list at a door. The bouncer reads it from the top, and the first line that describes you decides whether you get in. If your name is on no line at all, you do not get in: that last, unwritten rule is the implicit deny.

Self-Check Quiz (32 Questions)

Click a question to reveal the answer.

Q1. In which order does IOS check the lines of an ACL?

From the top down; it stops at the first line that matches.

Q2. What happens to a packet that matches no line?

It is denied by the implicit deny at the end of every ACL.

Q3. ACL 10: deny host 10.1.10.99, then permit 10.1.10.0 0.0.0.255. Can 10.1.10.99 get through?

No: line 1 matches first and denies it.

Q4. Same lines in the opposite order?

Yes: the subnet permit matches first; the host deny is shadowed and never hit.

Q5. What is the wildcard for 255.255.255.224?

0.0.0.31 (255 − 224).

Q6. What does a 0 bit mean in a wildcard?

That bit must match the address in the ACE.

Q7. Which addresses does 10.1.10.1 0.0.0.254 match?

The odd addresses .1, .3 … .255 in 10.1.10.0/24.

Q8. What does access-list 12 permit 10.1.10.0 255.255.255.0 really match?

Every address whose last octet is 0, anywhere: the mask was read as a wildcard.

Q9. What is the difference between standard and extended ACLs?

Standard matches the source address only; extended matches protocol, source, destination and ports.

Q10. Name the numbered ranges for standard and extended IPv4 ACLs.

Standard 1–99 and 1300–1999; extended 100–199 and 2000–2699.

Q11. What does access-list 11 deny 10.1.10.0 match?

Only the single address 10.1.10.0: a standard ACE without a wildcard is one host.

Q12. Why does access-list 150 deny tcp 10.1.10.11 gt 1023 host 10.1.20.20 eq 23 fail?

Extended ACEs have no default wildcard: the source needs a wildcard or the host keyword.

Q13. Which command creates a named extended ACL, and what does the prompt change to?

ip access-list extended NAME; the prompt becomes (config-ext-nacl).

Q14. deny tcp host 10.1.10.99 any: can GUEST still ping?

Yes: ICMP is not TCP. Use deny ip to stop everything.

Q15. Where does eq 443 go to match HTTPS requests to WEB1?

After the destination: … host 10.1.20.10 eq 443.

Q16. Why is filtering on the client’s source port risky?

Source ports are random ephemeral ports and vary by OS and application.

Q17. What does established match?

TCP segments with the ACK or RST bit set (replies), not initial SYNs.

Q18. Do you need the log keyword to see hit counts?

No: every ACE has a counter in show access-lists.

Q19. When is a log message sent for repeated matches?

The first match immediately; further matches as a summary about every 5 minutes.

Q20. What does log-input add?

The input interface and source MAC address.

Q21. An ACL applied in on Gi0/0 checks which packets?

Packets arriving on Gi0/0, before routing.

Q22. How many IPv4 ACLs can one interface have?

One inbound and one outbound.

Q23. Which command shows the ACL applied to an interface?

show ip interface Gi0/0 (Inbound / Outgoing access list lines).

Q24. In NAT, what does deny in the ACL mean?

The traffic is not translated; it is not dropped.

Q25. You type ip access-group 130 in on an interface that already has 120 in. What happens?

130 replaces 120: one ACL per direction.

Q26. Hosts must not Telnet to R2 behind R1. Which of R1 F0/0 in, R1 F1/0 out, R1 F0/0 out work?

F0/0 in and F1/0 out; F0/0 out never sees the requests.

Q27. Why can an inbound ACL on R2 block R1’s own Telnet while an outbound ACL on R1 cannot?

An outbound ACL does not filter router-originated traffic; R2’s inbound ACL sees all arriving packets.

Q28. Where should an extended ACL go, and where a standard one?

Extended near the source, standard near the destination.

Q29. How do you insert a line between sequence 10 and 20 in ACL 110?

ip access-list extended 110, then 15 followed by the ACE.

Q30. What does no access-list 110 deny tcp host 10.1.10.99 any do in global configuration?

Deletes the entire ACL 110.

Q31. Why add deny ip any any log at the end?

To count and log what the implicit deny would drop silently.

Q32. How do you turn an ACL into a block-list?

End it with permit any / permit ip any any.

If you can answer these without looking, you can read any ACL in front of you. If one surprises you, its answer points to the topic to reread.

What an ACL Is: ACEs, Actions and Matching

WHERE YOU DO THIS
⚙ Router · global configuration
R1(config)# — numbered ACL lines, ip access-list to enter a named ACL		access-list … (define)
🔌 Router · interface configuration
R1(config-if)# — ip access-group to apply an ACL in or out		ip access-group … in | out (use)

An ACL is a list of access control entries (ACEs). Each ACE is one line: an action (permit or deny) and a description of packets. The description can use:

  • source IP address (all ACLs)
  • destination IP address, protocol (IP, TCP, UDP, ICMP, OSPF …) and source / destination port (extended ACLs)
  • extras such as TCP flags, established, and logging (extended ACLs)

Writing an ACL does nothing by itself: it is a definition. It acts only when something uses it: an interface (ip access-group), the VTY lines, NAT, QoS and so on. By default, with no ACL applied, a router forwards every packet it has a route for.

▸ Run on: Router R1 · configuration (paste in config mode)access-list 10 permit 10.1.10.0 0.0.0.255     the definition: one ACE
interface GigabitEthernet0/1
 ip access-group 10 out     the use: filter packets leaving Gi0/1

ACLs exist on routers, Layer 3 switches and many Layer 2 switches. This guide says “router” throughout; the commands are the same on a Catalyst switch interface or SVI.

Writing the guest list and handing it to a door are two separate jobs. A list sitting in the office stops nobody; it only matters once a bouncer at a particular door is told to use it.

Where ACLs Are Used: Security, NAT, QoS and More

The same ACL syntax is used in two very different ways. In one, permit and deny mean “forward” and “drop”. In the others, they only mean “this packet is selected” or “not selected”.

The same list of names can be a guest list (who gets in) or a seating plan (who sits at the VIP table). Not being on the seating plan does not get you thrown out of the party; it just means you sit somewhere else.

How a Packet Is Checked: Top-Down, First Match, Implicit Deny

Three rules decide every ACL’s behaviour:

  1. Top-down: ACEs are checked in order, from the first line to the last.
  2. First match wins: as soon as a packet matches an ACE, that ACE’s action is taken and checking stops.
  3. Implicit deny: every ACL ends with an invisible deny any (standard) / deny ip any any (extended). A packet that matches no line is denied.

Consequences you will meet every day:

  • Order matters. Put specific lines (one host, one port) above general ones (a whole subnet). A general line above a specific one shadows it: the specific line can never be hit.
  • An ACL with only deny lines denies everything: the denies drop what they match, and the implicit deny drops the rest. Add a permit for what should pass.
  • An empty ACL (referenced but with no lines) permits everything on most IOS releases; once it has a single line, the implicit deny applies.
  • The implicit deny has no hit counter. To count (or log) what it drops, add an explicit last line such as deny ip any any log.
▸ Run on: Router R1 · configuration (paste in config mode)access-list 110 permit tcp host 10.1.10.99 host 10.1.20.10 eq 80     GUEST may browse WEB1
access-list 110 deny   ip host 10.1.10.99 any     GUEST: nothing else
access-list 110 permit ip 10.1.10.0 0.0.0.255 any     the rest of USERS: everything

The bouncer reads the guest list from the top and stops reading at the first line that describes you. “Guest: may go to the bar” on line 1 lets the guest in, even though line 2 says “Guest: not allowed anywhere”. And anybody the list never mentions is turned away by the rule nobody wrote down.

An ACL filters only after it is applied to an interface in a direction, always from R1’s point of view:

DirectionPackets checkedWhenLab example
inpackets arriving on that interfacebefore the routing decision: denied packets cost no routing workip access-group 110 in on Gi0/0: everything USERS send

  • One ACL per interface, per direction, per protocol (IPv4 / IPv6). A second ip access-group in the same direction replaces the first.
  • Replies count too: if PC1 talks to WEB1, WEB1’s replies arrive in on Gi0/1 and leave out on Gi0/0. An ACL that forgets the return direction breaks the conversation.
  • Traffic generated by the router itself (pings, routing updates, Telnet from R1) is not filtered by an outbound ACL on that router.

The guard on the in-lane stops people before they reach the lift; the guard on the out-lane stops them on their way out of that particular door, after they have already found their floor.

Subnet Mask vs Wildcard Mask

Both are 32-bit patterns written as four numbers, and for an ordinary subnet one is the other with every bit flipped. They answer different questions:

Subnet maskWildcard mask
Used forinterface addresses, routing (which part is the network)ACLs, OSPF / EIGRP network statements (which bits to check)
A 1 bit meansthis bit is part of the networkignore this bit (any value)
A 0 bit meansthis bit is part of the hostthis bit must match
/24 written as255.255.255.00.0.0.255
One host255.255.255.255 (/32)0.0.0.0 (or the word host)
Everything0.0.0.0 (/0)255.255.255.255 (or the word any)
Must the 1s be together?yes, always left-hand 1s then 0sno: any pattern is allowed (see why)

Typing a subnet mask where a wildcard belongs is the classic ACL mistake. access-list 10 permit 10.1.10.0 255.255.255.0 is accepted, but it means “ignore the first three octets, match .0 in the last”: it matches 0.0.0.0, 10.1.10.0, 192.168.7.0 … every address ending in .0, and not your subnet. IOS rewrites it as 0.0.0.0 255.255.255.0, which is your clue.

A subnet mask is a postcode chart: it says which part of an address is the street and which part is the house number. A wildcard is a stencil laid over the address: holes (0) are the digits that must match exactly, solid parts (1) are digits the bouncer does not bother reading.

Why ACLs Use Wildcards: Bits to Check, Not Network Size

If a wildcard is usually just an inverted subnet mask, why not use the mask? Because ACLs need to say which bits to compare, not where a network ends, and that is more flexible:

  • Matching one host and matching anything use the same mechanism as a subnet (0.0.0.0 and 255.255.255.255).
  • Non-contiguous patterns are possible. Wildcard 0.0.0.254 with address 10.1.10.1 checks every bit except bits 1–7 of the last octet, so it matches every odd address in 10.1.10.0/24. A subnet mask cannot express that.
  • Several subnets with one line: 10.1.0.0 0.0.254.255 matches 10.1.0.x, 10.1.2.x, 10.1.4.x … (even third octets): handy for “all user floors” if they were numbered that way.
  • The router compares only the bits where the wildcard is 0, so the check is a fast bit operation in hardware.

Non-contiguous wildcards work in ACLs on routers but are rarely a good idea in production: the next engineer may not read them correctly. Many Layer 3 switches also support them in hardware, but check your platform before relying on them.

A stencil can have holes in any pattern you like. A subnet mask can only say “the first N letters”; a wildcard can say “the 1st, 2nd and last letters, ignore the rest”. Most days you cut a simple stencil, but the option is there.

Shortcut: block size minus one

The wildcard octet is always block size − 1. A /26 has blocks of 64 addresses, so the wildcard is 63. A /20 moves in steps of 16 in the third octet, so the third octet is 15 and everything after it is 255.

Check the address too

The address in the ACE should be the first address of the block. 10.1.20.70 0.0.0.63 is not a block start (blocks are .0, .64, .128, .192): IOS keeps the bits it must compare and stores 10.1.20.64 0.0.0.63, which matches .64 to .127. ACL Traps: Missing Wildcards and Masks in the Wrong Place

WHERE YOU DO THIS
⚙ Router · global configuration
R1(config)# — numbered ACL lines, ip access-list to enter a named ACL		retype the ACE with its wildcard
🧰 This guide

Two mistakes look harmless when typed and catch everyone once.

1 · Standard ACL: forgetting the wildcard on a subnet

▸ Run on: Router R1 · configuration (paste in config mode)access-list 11 deny 10.1.10.0     meant: deny the whole USERS subnet

A standard ACE with no wildcard means one host. This line denies only the address 10.1.10.0 (the network address, which no PC uses), so it matches nothing useful and USERS still get through. Always type the wildcard for a subnet:

▸ Run on: Router R1 · configuration (paste in config mode)access-list 11 deny 10.1.10.0 0.0.0.255

2 · Extended ACL: no default wildcard

▸ Output on: Router R1 · global configurationR1(config)#access-list 150 deny tcp 10.1.10.11 gt 1023 10.1.20.20 eq 23
                                             ^
% Invalid input detected at '^' marker.

After a source address IOS expects its wildcard. gt is not a wildcard, so the line is rejected. Use a wildcard, host or any for both source and destination:

▸ Run on: Router R1 · configuration (paste in config mode)access-list 150 deny tcp host 10.1.10.11 host 10.1.20.20 eq 23

3 · A subnet mask instead of a wildcard

▸ Run on: Router R1 · configuration (paste in config mode)access-list 12 permit 10.1.10.0 255.255.255.0     accepted, but stored as 0.0.0.0 255.255.255.0

This matches every address whose last octet is 0, anywhere: not the USERS subnet (why). The decoder flags this pattern.

The guest list says “the Smith family” but you only wrote “Smith”: the bouncer reads that as one person called Smith, and the rest of the family walks in. Write the family part (the wildcard) every time.

Source Port vs Destination Port

A TCP or UDP conversation has two ports. Knowing which one is which decides where the port condition goes.

  • Destination port on a request = the service (80 web, 443 HTTPS, 23 Telnet). This is what you filter almost always.
  • Source port on a request = a random, temporary port chosen by the client (an ephemeral port). Modern Windows, macOS and Linux use the 49152–65535 range by default, but older systems and some applications use lower ports.
  • The source port is optional in the ACE; leaving it out means any source port, which is the right choice for client traffic.
▸ Run on: Router R1 · configuration (paste in config mode)access-list 120 permit tcp 10.1.10.0 0.0.0.255 host 10.1.20.10 eq 80     ACL 120 (in on Gi0/0): requests USERS → WEB1 web
access-list 121 permit tcp host 10.1.20.10 eq 80 10.1.10.0 0.0.0.255     ACL 121 (in on Gi0/1): replies WEB1 port 80 → USERS

Avoid conditions like gt 49151 on the client’s source port: a client using a lower ephemeral port simply stops matching, and the problem looks random. Filter on the server port instead.

When you phone a company you dial its published number (destination port 80), but the call shows up from whatever line your phone system happened to grab (a random source port). The company is listed in the directory; you are not.

  • GUEST lines come first: GUEST is inside 10.1.10.0/24, so the USERS lines further down would otherwise match GUEST too.
  • GUEST’s “everything else” (internet) is allowed by the last line; tighten it with deny ip host 10.1.10.99 any before the final permit if GUEST must have web only.

  • Applied in on Gi0/0, the ACL sees only USERS’ traffic, so replies from SERVERS to USERS are not affected.

Paste the ACL into the ACL Decoder and test: GUEST → 10.1.20.20:23 (GUEST deny towards SERVERS, logged), PC1 → 10.1.20.20:23 (Telnet deny, logged), PC1 → 10.1.50.5 (MGMT deny), PC1 → 8.8.8.8:443 (final permit). Remarks do not take part in matching.

Write the policy as sentences first, then turn each sentence into one or two lines, most specific person first (the guest), then the general rule for everyone in the room, then what is forbidden for everyone, then “everything else is fine”. The ACL is just the policy in the router’s grammar.

Where an ACL Can Be Applied: Following the Packet

WHERE YOU DO THIS
🔌 Router · interface configuration
R1(config-if)# — ip access-group to apply an ACL in or out		ip access-group 100 in (R1 F0/0) / out (R1 F1/0) / in (R2 F1/0)

A common question: “this ACL could go inbound on F0/0 or outbound on F1/0, so which is right?” Usually several points work. Follow the packet and check each interface it crosses, in the direction it crosses it.

Scenario (its own small topology, used only here): hosts in 10.2.1.0/24 sit behind R1 F0/0; R1 F1/0 connects to R2. Hosts must not Telnet to R2; everything else is allowed.

▸ Run on: Router R1 · configuration (paste in config mode)access-list 100 deny   tcp any any eq 23     Telnet to anything
access-list 100 permit ip any any     everything else passes
PointCommandStops hosts → R2 Telnet?Side effects
A R1 F0/0 ininterface f0/0 · ip access-group 100 in✔ yes, before R1 routes itAlso stops hosts Telnetting to R1 itself (an inbound ACL checks traffic addressed to the router) and to anything else beyond R1. Drops it earliest: no wasted routing.
B R1 F1/0 outinterface f1/0 · ip access-group 100 out✔ yes, after routingHosts can still Telnet to R1. Also stops Telnet from any other network on R1 heading out F1/0. R1’s own Telnet to R2 still works (router-originated traffic is not checked by an out ACL).
C R2 F1/0 inon R2: interface f1/0 · ip access-group 100 in✔ yes, at the destinationAlso blocks R1’s own Telnet to R2: on R2 that is just another arriving packet. The packet has already crossed the R1–R2 link.
D R1 F0/0 outinterface f0/0 · ip access-group 100 out✖ noOnly sees packets going towards the hosts. Telnet requests to R2 never leave through F0/0, so they are never checked.
R1 F1/0 in / R2 F1/0 out✖ no for requestsThese only see traffic travelling from R2 towards the hosts (replies and R2-originated traffic).

How to pick

  • List every interface the packet crosses and the direction: here F0/0 in → F1/0 out on R1 → F1/0 in on R2.
  • Each of those is a candidate. Choose by what else the ACL must or must not catch: should hosts still reach R1? Should R1 itself still reach R2?
  • With an extended ACL, prefer the point closest to the source (A): unwanted traffic is dropped before it uses the network. See Where to place standard and extended ACLs.
  • In our main lab the same reasoning applies: USERS-IN is applied in on Gi0/0 (point A for USERS).

Picture the route as a corridor with doors, each with an in-lane and an out-lane. You can post the “no Telnet” guard on any lane the request actually walks through: the entry from the hosts’ room (A), the exit towards R2 (B), or R2’s own front door (C). Posting him on the lane walking back into the hosts’ room (D) catches nothing, because the request never walks that way. Where you post him decides who else he turns away.

Where to Place Standard and Extended ACLs

Cisco’s long-standing guideline follows from what each ACL type can see:

ACL typePlace itWhy
Extendedas close to the source as possible (usually in on the source’s interface)It can name the exact destination and port, so it drops only the unwanted traffic, before it crosses the network.
Standardas close to the destination as possible (usually out towards it)It can only name the source. Near the source it would block that source from every destination.
  • These are starting points, not laws. Ownership matters too: you may only manage one of the routers.
  • Applying in, close to the source, also stops spoofed source addresses early (permit only the real subnet).
  • For device access (who may SSH to R1) a standard ACL goes on the VTY lines with access-class, not on an interface.

A guard who only reads the sender’s name must stand right at the door he protects, or he turns that sender away from every room in the building. A guard who reads sender and recipient can stand at the main entrance and still send each visitor only to the right rooms.

ACE Order in Practice: Specific Before General

The same two lines in a different order give opposite results, because checking stops at the first match (how a packet is checked).

ACLLines (in order)GUEST 10.1.10.99PC1 10.1.10.11
Adeny host 10.1.10.99
permit 10.1.10.0 0.0.0.255		✖ denied by line 1✔ permitted by line 2
Bpermit 10.1.10.0 0.0.0.255
deny host 10.1.10.99		✔ permitted by line 1✔ permitted by line 1

In B the deny is shadowed: it can never be hit, because every packet it describes already matched the permit above. IOS accepts it without complaint; show access-lists simply never shows matches on that line.

▸ Run on: Router R1 · configuration (paste in config mode)access-list 1 deny   host 10.1.10.99     specific first
access-list 1 permit 10.1.10.0 0.0.0.255     general after

Paste ACL B into the ACL Decoder: it marks line 20 “Never matches: line 10 above it already matches all of this traffic”.

Rules on a list are read like a recipe: the first instruction that applies is the one you follow. “Everyone from the users’ room may enter” written above “except the guest” means the guest is already inside before anyone reads the exception.

Implicit Deny, Explicit Deny All and Explicit Permit All

WHERE YOU DO THIS
📝 Router · named ACL mode
R1(config-std-nacl)# / R1(config-ext-nacl)# — the ACEs of a named ACL		deny ip any any log · permit ip any any as the last line

Three states to keep straight:

SituationResult
No ACL applied to the interfaceall traffic passes (the router forwards whatever it has a route for)
ACL appliedeverything is denied except what a line permits (implicit deny at the end)
ACL applied, last line permit anyeverything is permitted except what a line denies

Explicit deny all, for logging

The implicit deny has no counter and never logs. Many organisations end every ACL with an explicit deny so the drops are counted and logged:

▸ Run on: Router R1 · configuration (paste in config mode)access-list 1 permit 10.1.10.0 0.0.0.255
access-list 1 deny   any log     same effect as the implicit deny, but counted and logged
▸ Run on: Router R1 · configuration (paste in config mode)ip access-list extended USERS-IN
 permit ip 10.1.10.0 0.0.0.255 any
 deny   ip any any log     catches spoofed sources, visibly

Explicit permit all, to reverse the logic

To block a few things and allow everything else, finish with a permit for everything:

▸ Run on: Router R1 · configuration (paste in config mode)access-list 2 deny   10.1.10.0 0.0.0.255     block USERS
access-list 2 permit any     everyone else allowed
▸ Run on: Router R1 · configuration (paste in config mode)ip access-list extended NO-TELNET
 deny   tcp any any eq telnet
 permit ip any any

Anything you add below an explicit permit ip any any or deny ip any any is never reached. Insert new lines above it with a sequence number (sequence numbers).

An allow-list is a party with a guest list: if you are not on it, you are not coming in. A block-list is an open house with a short list of banned people. The invisible last line makes every ACL a guest-list party unless you write “everyone else welcome” at the bottom.

Traffic Sourced from the Router Itself

ACLs applied to interfaces act on traffic passing through the router. Packets the router itself generates are not checked by an outbound ACL on that router.

▸ Run on: Router R1 · configuration (paste in config mode)access-list 100 deny   tcp any any eq 23     no Telnet through R1 towards R2
access-list 100 permit ip any any
interface FastEthernet1/0
 ip access-group 100 out
  • Hosts in 10.2.1.0/24 cannot Telnet to R2: their packets are forwarded by R1 and checked on F1/0 out.
  • An administrator on R1’s CLI can Telnet to R2: those packets originate on R1.
  • Routing protocol hellos, NTP, syslog and pings from R1 are likewise unaffected by R1’s outbound ACLs.
  • Inbound is different: an inbound ACL also checks packets addressed to the router (Telnet / SSH / ping to R1). That is why an inbound ACL can lock you out of the router itself.
  • To control who may log in to the router, use a standard ACL on the VTY lines: line vty 0 4 → access-class 10 in.

The doorman checks visitors walking through the building. Staff who start their walk from inside the doorman’s own office (the router’s CLI) are not checked on the way out. But the next building’s doorman (R2’s inbound ACL) checks everyone who arrives, staff included.

Changing ACLs Safely on a Live Router

WHERE YOU DO THIS
⌨ Router · privileged EXEC
R1# — show access-lists, show ip interface, debug, clear counters		copy running-config flash: · reload in 10 · reload cancel
🔌 Router · interface configuration
R1(config-if)# — ip access-group to apply an ACL in or out		ip access-group NEW-NAME in
🧰 This guide
Decoder and wildcard calculator: paste and read, no router needed		decoder test before the window

ACL changes take effect the moment you press Enter. A wrong inbound line on the interface you are connected through can lock you out. A routine that avoids surprises:

  1. Write it offline as a named ACL with remarks, and paste it into the ACL Decoder: check for shadowed lines, wildcards, and test the important flows.
  2. Save a rollback point: copy running-config flash:pre-acl.cfg.
  3. Keep a way back in: console access, or a second session from a source you are sure the ACL permits. Optionally schedule a safety reload: reload in 10 (cancel with reload cancel once all is well; the reload brings back the saved startup configuration).
  4. Build the new ACL under a new name (e.g. USERS-IN-V2) while the old one keeps working.
  5. Swap in one command: ip access-group USERS-IN-V2 in replaces the old ACL on that interface in one step.
  6. Verify: clear access-list counters USERS-IN-V2, test the key flows, check the counters and show ip interface.
  7. Roll back if needed by re-applying the old name; remove the old ACL only after the change is confirmed.
▸ Run on: Router R1 · privileged EXEC + Router R1 · global configuration + Router R1 · interface configurationR1#copy running-config flash:pre-acl.cfg
R1#reload in 10     safety net while you change remotely
R1(config)#interface GigabitEthernet0/0
R1(config-if)#ip access-group USERS-IN-V2 in     atomic swap from USERS-IN
R1#show access-lists USERS-IN-V2
R1#reload cancel     only when everything works

Do not edit a live ACL by deleting it and pasting it back: between the two steps the interface has an undefined ACL (permit all), and if you paste only half, the implicit deny applies to the rest. Edit with sequence numbers, or swap names as above.

Rehearse the new guest list on paper, print it under a new title, and then swap the clipboard at the door in one move, while a colleague stands by with the old list. If the queue stops moving, you hand the old list back.

  • It reads interface + ip address lines and ip route statements, and uses the longest match to find the interface towards each address (a default route counts).
  • It only looks at this router. If the source and destination are behind the same interface, the traffic never crosses the router and no ACL here can filter it.
